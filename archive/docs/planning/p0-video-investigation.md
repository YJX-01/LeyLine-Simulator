# P0 视频定位小验证

日期：2026-11-06。范围：定位风险验证，无 UI、无产品视频模块，不阻塞无视频 P1 求值。

## 复现与证据

在仓库根运行 `node tools/scripts/probe-video-timing.mjs`。此可选调查工具需要 PATH 上的 `ffmpeg`、`ffprobe`、已安装的项目依赖及 Playwright Chromium；不成为默认测试或构建依赖。脚本生成临时 64×64 WebM，用 FFprobe 读取实际帧时间戳，再将本地内容作为 data URL 交给 Chromium；不访问网络、不保存媒体产物，结束清理自身临时目录。没有使用外部参考库或安装脚本。

实测环境：Windows，Node 25.9.0，pnpm 11.3.0，FFmpeg 9.0，Playwright Chromium 156.0.8078.4。该 Node 高于仓库最低版本；不能将本试验理解为已经覆盖 CI Node 24 或全部浏览器。

合成输入从 30 fps 素材中仅保留原帧号 0、1、3、6、10、15，全部编码为关键帧，使用 VFR 输出。FFprobe 独立观测到展示时间戳为 `[0, 0.033, 0.100, 0.200, 0.333, 0.500]` 秒。脚本断言这些值，并断言下表前三次展示时间。

| 请求 currentTime（秒） | 读回 currentTime | requestVideoFrameCallback 的 mediaTime |
| --- | --- | --- |
| 0.100 | 0.100 | 0.100 |
| 0.13333333333333333 | 0.133333 | 0.100 |
| 0.200 | 0.200 | 0.200 |
| 0.333 | 0.333 | 0.333 |
| 0.500 | 0.500 | 0.500 |

`requestVideoFrameCallback` 可用，`fastSeek` 在此 Chromium 不存在。第二行证明请求时间前移一个名义 30 fps 帧长，展示帧仍可能不变；`currentTime` 也不能单独证明已经展示下一帧。此样本刻意全关键帧，故问题不是长 GOP 导致的解码延迟。

整数毫秒另有量化风险：若每次累加 `round(1000/30)=33 ms`，300 步得到 9900 ms；从绝对帧号计算 `round(300×1000/30)` 才是 10000 ms。脚本对此也有断言。项目整数时间应由原始绝对媒体时间映射，避免累计舍入误差；仍需保留原始定位依据，不能把整数毫秒当作视频精确帧身份。

## 能力限制与后续约束

本试验已验证 Chromium 上合成 VP8/WebM 的暂停 seek、展示回调与 VFR 反例。没有验证任意视频的准确逐帧前进或后退，也没有验证真实录屏、长 GOP、损坏文件、音视频不同起点、可变播放速率、丢帧、后台标签页、隐私时间精度限制、Firefox/WebKit 或大文件性能。不能据此宣传跨浏览器逐帧能力。

P7 若只基于 `currentTime += 1/fps`，最多应称为按名义步长定位。准确帧选择需要真实 PTS/帧索引；展示完成需要验证实际呈现帧，而非仅等待 `seeked` 或读回请求时间。回调提供观测证据，不提供帧索引，也不独自完成倒退一帧。`fastSeek` 即使在其他环境可用，仍须独立验证其近似定位行为，不能把它作为通用精确接口。

后续先使用实际录屏与稀疏关键帧样本，跨三浏览器验证，再决定媒体索引/解码方案及成本；本轮没有引入 WebCodecs、WASM 解码器或完整 UI。轴只依赖项目时间，视频定位信息应作为独立可选关联保留，视频不可用不阻塞保存和计算。
