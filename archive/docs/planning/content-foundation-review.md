# F0方案审查：规范、适用性与范围

审查日期：2026-11-10。对象是本次对话中第一版 `content-foundation.md`，结论已落实到该文件r2及实施提示。本审查记录的是施工前的方案修订；随后用户授权实施，实际范围和验证见[F0记录](f0-implementation.md)。

## 审查结论

上一版具备数据/实例分离、类型单一来源、显式版本和兼容迁移等合理方向，但不能直接作为施工方案：它把目录整理扩张成内容包平台、工程级引用改造和求值框架升级，缺少收益证据与分步边界。应保留必要基础工作，撤回无现实消费者的前置设计。

“业界规范”在此分为格式规范、工具约束和工程实践。JSON有正式格式规范，TypeScript/Zod有明确工具行为；目录名称、数据库选择、类或声明式配置、快照是否去重，属于需要结合项目约束作出的工程选择。一个成熟项目的实现不能作为这些选择的规范性证明。

## 发现与处理

P1表示会显著扩大实施风险或改变产品语义，P2表示设计依据/可维护性不足；这是本次方案风险排序，不是运行中产品漏洞评级。

| 编号 | 风险 | 上一版问题与代码依据 | 修订 |
| --- | --- | --- | --- |
| R1 | P1 | F0.4强制新轴格式、内容引用去重和完整升级差异；当前`RealBuild`完整内嵌快照已能离线计算，尚无文件体积或加载瓶颈测量 | 撤回项目格式变更和去重前置，保留schemaVersion 1及当前快照；后续有必要时单独决策 |
| R2 | P1 | 把新内容包/求值计划层列为已支持规则的迁移目标，并提出各乘区进入统一依赖；虽声明先等价迁移，却未明确哪些属性扩展属于当前必须。P3节点及`evaluateRealDamage`已有可用分派 | 保留同一engine和已支持语义，只抽离现有规则；复杂机制按P5真实需求逐项扩展 |
| R3 | P1 | 用“统一内容包”覆盖编写、导入、快照和求值，却未明确交换对象与内部运行对象的转换边界，容易被实施为同一物理模型；上一版并未明文要求对象形状完全相同，此项属于需消除的设计歧义 | 共享字段语义及校验契约，通过明确转换连接交换对象与运行时对象；已支持规则完整导出，内部缓存/索引/函数不直接序列化 |
| R4 | P2 | 提出ContentPackage、包级身份和依赖模型，却未区分自包含导出文件与可独立安装/解析的包系统；前者是实际需要，后者未有消费者。上一版并未明确要求远端包安装，此处是范围风险 | 先提供有类型/版本的自包含定义文件，复用现有ID/version与所用快照；明确排除包管理或插件解析平台 |
| R5 | P2 | 已提schema与校验，但未明确`satisfies`静态检查、生成/导入的运行时解析、领域合法性及执行检查分别位于何处，builder也未证明必要 | schema推导类型；生成/外部导入时运行时解析，再做单位、引用、合法性、环与预算检查；builder非必需 |
| R6 | P2 | 上一版已认可JSON，没有要求数值全改TS；但把规则TS化作为默认路线，且目录取舍缺少“项目约定与正式规范”的界定 | 明确JSON本身符合交换实践；目录归位是本仓库职责选择。数值保留JSON，规则按复杂度选校验过的配置或TS纯对象，不把TS化当作质量保证 |
| R7 | P2 | “语义哈希/版本”未明确哈希对象，目录迁移又可能改变manifest | 沿用LF归一化文件SHA-256及原版本口径；另行核对语义等价，不能把字节校验称作语义/机制正确性，也不另造通用规范化算法 |
| R8 | P2 | F0.2已写逐组同步消费者，F0.5又写产品接线，阶段职责交叉；存在把规则/格式消费者延后到第五步才验证的风险 | 每个输入族/规则族同时迁移直接消费者，保留旧入口适配直至调用者完成切换；第五步仅收口 |

另保留一个需要后续观察的现状：`real.ts`按目录位置计算分块位置。它与当前生成器配套，不能凭此断言已有错配；迁移须核对每个ID的加载结果，确有维护收益时由生成器输出ID到块的索引，不先建通用仓储框架。

## 外部依据与适用范围

1. [RFC 8259](https://www.rfc-editor.org/rfc/rfc8259)定义JSON的数据表示，数组有序，数字有范围与互操作性约束，也允许解析器限制输入大小/深度。它不规定仓库目录或要求数据库。由此不能将“使用docs下的JSON”判为违反JSON规范。
2. [TypeScript satisfies说明](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-4-9.html)说明其作用是检查表达式类型并保留推断；[Zod基础文档](https://zod.dev/basics)分别提供运行时parse/safeParse与z.infer类型推导。结合本项目的外部JSON入口，静态检查不能替代运行时解析。
3. [DTO模式原文](https://martinfowler.com/eaaCatalog/dataTransferObject.html)说明可序列化传输对象通过转换连接领域对象。它源于远程调用，本项目仅借鉴其序列化边界，不能据此推导必须多建一套大型领域模型。
4. [Parallel Change](https://martinfowler.com/bliki/ParallelChange.html)描述先扩展、再迁移、最后收缩旧接口的工程方法。本项目用于逐消费者迁移，不意味着允许长期双写两份canonical。
5. [YAGNI](https://martinfowler.com/bliki/Yagni.html)讨论无现实需要的能力会产生开发、延迟与维护成本。这是工程实践观点，不是强制标准；撤回包管理、通用编译器等前置是本次结合项目规模作出的判断。
6. [Reproducible Builds定义](https://reproducible-builds.org/docs/definition/)以相同来源、环境和指令重建相同产物为依据。F0应记录实际Node/pnpm/工具链和生成命令，普通生成离线可重现；来源捕获/更新另行联网并记录，不混为同一动作。
7. [RFC 8785](https://www.rfc-editor.org/rfc/rfc8785)描述JSON规范化，是Informational RFC。只有未来确需跨实现一致的对象哈希时再评估；本次文件SHA-256无需为此引入新规范化层，数组仍保持语义顺序。
8. [JSON Schema dialect说明](https://json-schema.org/understanding-json-schema/reference/schema)中的`$schema`标识schema本身采用的方言。它与本项目文档的schemaVersion、dataVersion和rulesVersion不是同一件事；若导出编辑器用schema，必须写清适用方言，领域引用/单位校验仍由应用执行。

## 复查后的实施口径

- 必做：生产数据归属、schema复用、边界与语义校验、现有机制抽离、来源/离线生成、可格式化导出与往返、现有UI及旧文件回归。
- 条件触发：新文档版本、内容去重、动态乘区扩展、编译缓存、IndexedDB或数据库、远端包解析；每项须有实际需求及兼容方案，不属于F0默认出口。
- 明确保留：已有schema/rules分派、完整配装快照、真实库存/展柜隔离、P3捕获/历史/同刻顺序、缺资料与未支持机制的显式状态。

本次审查保留历史方案取舍；用户随后决定JSON优先，当前执行见[F0方案r3](content-foundation.md)与[实施提示](implementation-agent-prompt.md)。这次审查不构成实现验收，不扩充P5/P6支持范围；U1现已由用户明确确认结束。
