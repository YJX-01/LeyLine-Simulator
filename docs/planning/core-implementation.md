## 1. 实现取向

建立“轴记录 + 内容定义 + 配装候选 → 可解释的计算计划 → 目标函数值”的通用内核。正式内容和用户定义走同一条编译与求值路径。

先完成一个能保存、重新打开和换装求值的小闭环，再逐项扩充语义。快照、计数器、累计伤害和自定义公式是核心需求，需要早期算例验证，不留到大量角色接入后补救。

不恢复此前角色运行回调拆分，不以 `simulateCombat` 为新产品必经入口。现有调度器可供确定性和时间处理参考，但新内核只处理用户已提供的记录及其计算依赖，不自动补充命中。

## 2. 代码放置与包依赖

保留现有四个 workspace。本节目录是建议落点，不要求一次建立所有空目录。

```text
src/schema/src/workbench/
  common.ts             ID、时间、来源、单位、诊断契约
  expression.ts         可保存表达式、条件和读取方式
  definition.ts         角色/武器/套装/敌人及公共规则定义
  timeline.ts           动作、伤害、状态、阶段与可选元素球记录
  configuration.ts      实物库存、理论输入、配装及锁定
  objective.ts          单一目标、筛选与显式约束
  project.ts            项目文件、版本清单、人工修订
  evaluation.ts         求值结果、来源明细与完整性状态
  worker.ts             新工作台任务协议

src/engine/src/workbench/
  content/              定义注册、引用校验、能力与版本检查
  expression/           AST 检查、依赖收集、编译和基础求值
  attributes/           配装属性及具名属性转换
  timeline/             时间索引、状态/阶段查询、同刻排序
  effects/              规则实例化、叠层覆盖、修订合并
  compiler/             属性/快照/历史依赖展开、目标闭包、诊断
  evaluation/           复盘、期望、结果与来源轨迹
  optimization/         候选空间、约束、搜索协议与算法桥接
  analysis/             贡献、效果差异及属性增量收益
  project/              项目语义校验、恢复与升级预览
  index.ts              少量稳定的工作台公共 API

src/game-data/src/workbench/
  presets/              同契约的内置定义及敌人阶段元数据
  manifest.ts           定义版本、来源、验证状态和依赖清单

src/web/src/
  domain/workbench/     编辑命令、导入适配、本地仓储端口与任务控制
  stores/               响应式项目、候选配置与结果状态
  composables/          视频时钟、快捷键与任务生命周期协调
  components/workbench/ 时间轴、定义编辑、效果/诊断/分析面板
```

所有跨包引用走 `@leyline/*` 公共导出，新增公共入口时同时更新架构检查。`schema` 不导入 engine/game-data，game-data 不导入 schema；静态预设在 engine 加载边界使用 schema 校验，并有生成/一致性检查，避免为类型共享制造包循环。web 的 domain 不依赖 Vue/Pinia。

schema 内按 `common → expression → definition/timeline/configuration → project` 等单向依赖组织；项目、Worker、运行时结果不反向成为表达式的依赖。AST 的类型递归与模块循环分别处理。

## 3. 契约先行：可保存输入与运行时结构分开

使用 Zod 定义文件边界和相应 TypeScript 类型，外部输入始终以 `unknown` 进入。结构校验后再进行引用、版本、单位和语义校验，返回可定位的诊断，不用 `as unknown as` 绕过检查。

| 契约 | 实现要点 |
| --- | --- |
| 标注项目 | 稳定 ID，动作与伤害独立，视频可选；观测数值不充当公式值 |
| 内容定义 | 使用可扩展的定义 ID 和版本引用，不以五角色枚举作为新系统准入条件 |
| 配装候选 | 区分圣遗物实例 ID 与属性相同的另一件装备；理论属性不冒充库存实物 |
| 人工修订 | 保存来源记录、规则版本、效果局部键与覆盖内容，不覆盖自动结果 |
| 时间与状态 | 整数时间、显式顺序、区间端点；绝对生命与生命比例分别表达 |
| 项目版本 | 文件 schema、表达式语义、内容定义、规则操作版本分别记录 |

编译产物可以包含 Map、索引、数值数组和运行时缓存，不要求与 JSON 文件形状相同。派生结构不作为唯一保存依据，重开项目必须能从原始输入与定义重建。

为新模块启用明确的索引检查策略：数组/字典查找返回可缺失值并检查，表达式操作使用可穷尽联合，不盲目添加非空断言。是否全仓启用更严格编译选项另行迁移，不能为完成本模块掩盖旧代码问题。

## 4. 表达式与求值内核

### 4.1 外部 AST 与内部计划

外部 AST 使用带 `kind` 的受控节点，例如 `constant`、`input`、`add`、`multiply`、`clamp`、`if`、`statAt`、`snapshot`、`damageRef`、`windowSum`、`counterAt`。节点 ID、字段和可用操作都版本化；不支持原始 JavaScript、`eval` 或 `new Function`。

先用纯 TypeScript 解释器实现确定性求值。表达式经校验、引用解析、依赖提取后编译为带节点编号与来源映射的计划，再按拓扑和时间依赖执行。先不做代码生成、JIT 或大而全的公式语言。

单位校验至少区分固定属性、比例、倍率、时间和伤害等领域类别，并给不同属性设置可读类型。允许哪些乘除转换由操作签名定义；不能只因运行时都是 number 就允许任意相加。

### 4.2 已知、未知和错误

求值结果采用可区分状态，概念形式为：

```ts
type ValueResult<T> =
  | { status: 'known'; value: T }
  | { status: 'unknown'; reasons: DiagnosticRef[] }
  | { status: 'invalid'; errors: DiagnosticRef[] };
```

未知不是 0、false 或 NaN。数值必须有限，除零、缺失引用和不支持的规则产生明确诊断。条件使用真/假/未知语义，分支惰性求值；已知未选分支的缺失输入不应阻塞当前结果。仅在所有分支语义一致且可证明时合并未知分支。

复盘时缺失事实保持未知；期望口径下“明确使用暴击概率”是已定义的计算方式，不等于猜测视频是否暴击。缺失反应标注也不能被概率求值器自动补成某种反应。

### 4.3 来源与预算

节点记录定义、规则、标注、属性、时刻和读取阶段。普通搜索返回紧凑结果；用户请求明细时，由同版本同输入重新求完整轨迹，避免每个候选都保存庞大日志。

对表达式深度、节点数、历史展开、概率状态数设置显式预算。超预算返回原因，不改用不说明的近似或截断。每次求值持有独立状态，禁止可变内容单例。

## 5. 内容定义、属性与效果规则

### 5.1 共享定义与注册

`DefinitionRegistry` 接收内置或用户定义，完成结构、版本、ID 唯一性、引用和能力校验后返回只读定义集合。来源/验证状态是元数据，不形成另一套计算路径。

合成角色先通过普通定义验证全链路。内置真实角色随后以同格式接入。新内容若必须增加公共操作，先增加操作契约与独立算例，再注册该内容；不以 `if (character === ...)` 蔓延到编译器和优化器。

### 5.2 配装与属性

P2.5 已由 `engine/src/real-game.ts` 的 `resolveRealBuild` / `evaluateRealDamage` 解析采用的真实快照，`workbench/index.ts` 的受控 `game-damage` 节点调用同一数学。P3 应将这些基础属性与通用效果/捕获/历史依赖衔接，不能复制第二套伤害公式。使用具名参数，在数据转换边界隔离原始数组列号。旧模拟器 `loadout.ts` 可供参考，其五角色校验和硬编码效果不能直接成为新通用入口。

修饰需明确相加池、独立乘区、覆盖组、上下限和转换阶段。跨角色属性转换进入依赖图；不是先把每个人的最终面板全部算完，再尝试处理互相引用。

### 5.3 候选、实例与条件分离

建议拆成三个纯步骤：

1. `collectEffectCandidates`：由队伍、命座、武器、套装提供可选效果定义。
2. `instantiateEffectRules`：由已标注动作/伤害/状态生成带时间和来源的实例或条件节点。
3. `applyEffectOverrides`：合入用户禁用与修订，来源失配产生待确认项。

生命周期、覆盖和层数规则共享实现。涉及伤害累计的生效条件保留为图依赖，不在推导阶段假定已知；更换武器/套装时重新选择定义并检查修订引用。

## 6. 时间、快照与历史量

时间查询提供 `stateAt`、`enemyPhaseAt`、效果区间及记录索引。项目同刻顺序稳定，规则使用显式的读取阶段；默认区间提案为 `[start, end)`。阶段未知、区间冲突或空档不能随意延用某个敌人阶段；互斥阶段和可叠加效果用不同规则校验。

快照不是复制最终面板：`CaptureSpec` 指定捕获动作/效果、时刻、阶段与属性集合，编译成对应引用。其余乘区继续动态读取。对每个候选重新计算快照值，并明确是否排除效果自身等读取语义。

计数器和累计量用明确的 `initial / observe / accumulate / settle / reset` 契约。编译器从已记录事件按顺序展开状态节点；聚合窗口显式声明左右边界、角色/伤害类型筛选和结算伤害是否参与。不生成记录之外的攻击事件。

首版可使用直接扫描构建可读依赖边，再按已测负载优化为时间索引或前缀和。优化只能在语义相同的聚合类型上进行，不能跨重置、过滤或未知条件错误复用累计值。

## 7. 编译入口、求值入口与缓存

公共 API 的职责建议如下，名称可在实现时收敛：

| API | 职责 |
| --- | --- |
| `validateProject(input)` | 解析保存数据，检查引用和版本，允许可编辑但未补全的状态 |
| `prepareProject(project, definitions)` | 构建只读时间索引、稳定定义引用和公共依赖信息 |
| `compileCandidate(prepared, candidate, request)` | 绑定配装、展开效果/快照/历史依赖、编译目标并诊断 |
| `evaluatePlan(plan, options)` | 返回目标值、逐点结果、有效性及可选来源轨迹 |
| `checkOptimizationReadiness(space, request)` | 检查目标依赖和候选专属条件，返回就绪或待确认 |
| `compareEvaluations(a, b)` | 对齐记录与效果来源，生成配装/Buff/伤害差异 |

纯求值函数不读浏览器、不发网络请求。缓存键包含项目修订、定义内容签名、语义版本、候选配置、修订、目标与口径；换武器可能需要重编译，不假定全体候选共享相同图。

先做正确的全量编译/求值。后续按依赖签名复用不变子图；拓扑不变的候选可以绑定数值输入快速求值，拓扑不同则使用新的计划。任何缓存优化都与无缓存解释器对照。

## 8. 复盘与期望

复盘只读已标注事实。期望模式分层实现：独立线性伤害采用解析期望；相关触发、计数阈值及快照使用可验证的有限状态/分支求值。概率来源有稳定身份和明确依赖，不能将同一次触发在不同读取点当作相互独立的随机事件。

概率状态以 `(状态, 概率, 所需累计量)` 等形式表达，只有未来行为与收益所需信息等价时才可合并。对非线性累计结算、状态相关伤害等，保留足够的联合信息；不以 `f(E[X])` 冒充 `E[f(X)]`。

先用小规模枚举作为独立参考校验解析和状态求值。超出已实现语义或预算时明确报不支持。采样或其他近似不作为首版静默退路；若后续加入，应有单独口径、误差说明和可复现配置。

## 9. 优化与外部接入

`OptimizationProblem` 组合候选空间、目标、锁定、合法性及可选约束。候选提供者区分实物组合与理论参数，求值器共用；跨角色装备占用在全队候选上校验。

先实现小库存穷举参考搜索，证明相同目标与候选范围下的正确结果，并验证未知/非法候选处理。它用于回归与算法对照，不作为大库存最终性能方案。

莫娜格式/算法调查提前进行，固定上游版本并记录许可、字段、百分比单位、实例身份、公式回调、全队约束、运行时要求及适用限制。核心边界保持“候选 + 求值器”，在算法可用的接口处桥接；如果上游绑定面板或专属计算模型，先提交适配论证，不能把时间轴函数降级成错误的静态评分。

本地参考已放在被忽略的 `.references/`：社区莫娜、genshin-db、KQM TCL 与 Meropide 页面。按[来源清单与阅读指南](../references/README.md)使用固定提交，研究可以并行，不让外部 checkout 成为构建或测试隐式依赖。

搜索结果包含目标值、候选、约束、评估数、完整性、终止原因和最优性依据。启发式称“已找到的最好方案”，穷举完整覆盖才可按证据称该范围的最优。取消后不能发布完成状态，未知条件不能静默排除后宣称覆盖全范围。

导入适配放 web domain，网络访问通过端口注入；规范化纯函数可独立测试。公共角色接口尚未选定，先用本地快照/合成输入推进，不将接口选择变成内核开发阻塞。

## 10. 编辑、Worker 与保存

编辑命令由纯 `reduceProject` 处理，如增删记录、移动片段、替换配置和修改定义。ID 生成与时钟由调用侧提供，命令应用可重放，事务用于片段复制/撤销，不能撤销一半关联数据。

Pinia 只管理编辑状态和结果关联；视频与快捷键转换成同一套命令。动作层切换角色与伤害层选择标注角色是不同命令，不互相污染。

Worker 请求携带任务 ID、项目修订和输入签名，支持求值、分析与搜索。沿用现有代次隔离与 terminate 取消思路，搜索进度分批上报；过期结果不覆盖新轴。端口协议与 UI 解耦，预算到期与用户取消分别报告。

本地仓储通过端口实现，项目数据和大库存可按规模选择浏览器存储，文件导入导出始终可用。保存前后使用相同 schema，未知条件允许保存，非法引用需诊断；不静默覆盖读取失败的原始文件。

保存包包括实际使用的定义副本和内容签名、用户定义、配装/库存快照、人工修订、目标及版本清单。优先只实现一个明确的 v1 语义，再建立版本选择接口与恢复测试；后续变更不能就地改写旧版本实现。

## 11. 分析与可验证性

贡献按记录归属汇总，乘区明细来自公式轨迹；自定义公式可用节点标签注明乘区，但不强行把任意表达式拆成固定游戏公式。缺少语义标签时展示表达式依赖而非捏造乘区。

属性收益以显式增量重新求目标，必要时重新编译条件和快照，不只求静态面板导数。理论增量与库存可达收益分别标记，不把不同词条的任意单位当作公平成本。

测试以[总体设计三例](overall-design.md#7-三个独立算例验证提案)为主线，增加独立的概率枚举、微型库存穷举、版本往返和真实浏览器编辑流程。记录每个内容定义所需能力与验证算例，未覆盖项不能标为完整支持。
