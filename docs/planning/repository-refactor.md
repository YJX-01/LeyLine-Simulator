# 仓库结构与角色定义重构方案

日期：2026-11-10。状态：**已按用户最新决定移除旧数据迁移、补齐角色文本，相关本地验证通过**。以下审查证据描述批准前基线；当前结果、实施取舍及材料缺口见[实施记录](repository-refactor-implementation.md)。

本方案覆盖此前基础整理中未解决的职责、历史内核、数据模型和资源归属问题。之前的目录搬迁、JSON统一及局部校验是已有增量，不表示本方案已完成。U1已经由用户确认结束，不重开其验收。

本次审阅补充：角色内容模型参考成熟项目的实际定义，不以资源引用或来源字段作为角色设计主线；增加docs整理、已认可范式的固定，以及tools整体整理。以下为同一份计划的更新，不另起平行方案。

## 一、逐项结论与当前证据

| 用户问题 | 审查结论 | 本方案决定 |
| --- | --- | --- |
| schema是否应拆成单元 | 当前real-game.ts混合角色、武器、套装、配装、敌人与伤害，workbench/index.ts混合表达式、效果、项目与校验。按内聚概念拆分合理；不为每个字段创建一个文件 | 按内容、账号、项目、文件交换与任务协议拆分；复用同一原子契约并从schema推导类型 |
| legacy是否真正归档 | 没有。schema/index.ts仍导出legacy/combat/team；engine/index.ts仍导出旧模拟器；game-data根入口仍包含旧琴技能与content；旧表仍被生成、捕获、性能和发布脚本读取 | 停止所有正式依赖，将退出的实现、旧表、测试及工具一起归档；不保留第二套运行内核 |
| 阶段名称是否合理 | 当前evaluateP3、P3Read、p3.ts与规则字符串出现在正式实现、类型和诊断中，不能表达业务能力 | 改为属性求值、效果实例、捕获、累计、时间轴等语义名称；阶段标签只留历史记录 |
| tests放在源码中是否错误 | 并置测试和集中测试都可行；目前38份单测与源码并置，另有tests/unit和浏览器脚本，约定混用增加查找成本 | 本项目统一tests，按层和模块组织，src中不保留测试或测试辅助实现 |
| fixtures是什么 | 固定输入、参考输出、录存响应和边界资料；当前还混有旧内核合成场景、性能记录与当前产品输入 | 当前仍使用的真实录存并入tests/fixtures；历史构造场景及专用测试/辅助代码直接删除；取消根fixtures目录和跨目录测试脚本 |
| 素材为何分散 | public图片、src/assets装饰、web/data/icons来源与矢量、generated图标索引各有物理位置，但缺少一个可维护的资源入口 | 所有可维护资源及来源索引集中根assets；构建复制和运行索引明确为生成物，不再各自编辑 |
| 角色JSON是否直接使用 | 正式数值由real.ts加载，随RealBuild进入resolveRealBuild/evaluateRealDamage，确实参与计算；但介绍/被动/命座文本缺失，培养显示还读独立character-talent-display表 | 将角色定义改为同时包含文本、参数、结构化规则与能力状态，展示、培养、计算和导出共同消费 |
| 能否提高精度 | genshin-db具有参数、基础值和曲线，但不能由此断言所有值未经舍入；当前主词条来源仍是旧ArtifactStat.json | 逐字段审计精度与来源，替换旧表依赖；不插值补精度、不将浮点尾数当作更高可信度 |
| 文档及既有范式 | 当前docs混合现行规范、设计提案、阶段记录、过时能力与重复说明，已认可的交互和数据边界分散在多处 | 按规范/架构/操作/机制/研究/计划分类；每条约定一个权威入口，历史归档，明确实施状态并校验链接和命令 |
| tools分类 | 捕获、生成、检查、打包、发布、实验与桌面测试平铺；tools/desktop还承载应用运行代码 | 按任务分组维护脚本；应用代码回应用、测试回tests、退休及无当前消费者的脚本归档；固定命令接口 |

### 已核实的具体缺口

- 当前`data/characters/jean.json`顶层只有身份、数值、技能名/倍率、静态修饰、支持状态和来源，没有角色介绍、完整技能说明、被动和命座定义。
- 固定genshin-db提交的中文characters/jean.json已有title/description；talents/jean.json已有技能、被动说明和参数标签；constellations/jean.json已有六个命座说明。当前capture脚本主动只选少量字段，丢掉了这些资料。
- CharacterForm及角色头像组件使用独立生成的character-talent-display.json，其中命座加级依赖中文描述匹配；它没有和正式角色规则建立可验证的统一绑定。
- `benchmark-engine.mjs`仍调用simulateTeam并读取旧场景；`prepare-release.mjs`仍读取generated/legacy/content.json并将旧team规则写入发布清单。仅删除旧UI无法隔离这些依赖。
- `capture-real-game-data.mjs`仍从legacy/ArtifactStat.json捕获主词条。该依赖必须找到可验证替代来源，不能仅把文件改名或把数值复制后假称新来源。

正式依赖方向固定为：schema不依赖其他工作包；game-data依赖schema；engine依赖schema，输入由调用者提供完整快照；web依赖三者。清理旧内核后移除engine对game-data的直接依赖，让计算不暗中读取全局目录。

schema按可独立理解、复用和验证的概念拆文件，根index.ts只聚合公共导出，不放整套对象或计算实现。不将同一结构再手写一份interface；使用Zod推导类型。全项目禁止跨包相对导入及生产代码反向依赖tests/archive。

桌面与网络服务代码属于应用，移出tools/desktop，放到web/desktop及web/server。所有测试断言与浏览器/桌面流程放到tests；tools可以启动测试命令，但不再藏另一套测试实现。

生成目录可由普通命令离线重建，不提交运行分块、资源索引或构建副本。dev/build/typecheck/test命令显式准备输入；CI在检查前准备输入。生成器仅允许写上述generated目录、构建中间目录和交付产物，不覆盖维护输入。源码到同包generated的读取作为明确生成依赖登记在架构检查中。

## 三、统一角色定义：文本、数值、规则共同使用

### 参考成熟项目的内容组织

优先参考已有GenshinTools、genshin-db，以及莫娜项目中与本次定义有关的内容模型；对照实际文件和消费者，不仅记录目录结构。参考结论用于选择字段、数值组织和规则绑定，不直接复制其类层次、注册副作用或执行架构。

本轮已进一步核对本地GenshinTools固定提交：`src/domain/models.ts`中的CharacterKit包含skills/passives/constellations/glossary，技能详情由label/template组织；`src/domain/reference/stats.ts`中的CharacterStats包含培养档位与按等级排列的talent参数；`src/domain/combat/damage/impl/`读取这些参数建立实际公式和效果。它体现了角色内容应覆盖什么，以及参数怎样被展示与计算使用；本项目仍按既有需求统一为可导出的角色JSON。

实施时以琴、行秋、胡桃对照已存在的角色字段和消费者，先完成“采用哪些组织方式、如何接入当前模型、哪些不适用”的简短映射表，再落实共同schema。固定数值和文本由当前可验证数据取得，不把参考实现自动当作机制真值。

### 同一种角色定义

内置角色与自定义角色使用同一CharacterDefinition契约、同一校验与求值入口。复制内置角色后修改ID、修订并保留简短派生关系；导出保持同一字段结构，不再将内置资料与自定义角色建成两套模型。

新角色文件固定采用`schemaVersion: 2`、`kind: character-definition`，内容主体按`identity/attributes/progression/talents/passives/constellations/capabilities`组织，另保留必要的`id/revision/dataVersion`、简单origin标识及可选derivedFrom。origin只区分内置和自定义；用户修改不冒充游戏已核验内容。内置JSON和自定义JSON就是该定义本身，不再使用另一层包裹character的不同格式。

| 单元 | 必须表达的内容 | 实际消费者 |
| --- | --- | --- |
| identity | 中文名称、称号、介绍、元素、武器类型、星级等已有真实资料 | 角色页、选择器、详情 |
| attributes/progression | 基础数值、成长、突破与培养约束，单位明确 | 培养表单与属性解析 |
| talents | 三类技能的名称、说明、参数标签、等级数值、命中定义、冷却/消耗等已取得参数 | 技能说明、培养与伤害记录 |
| passives | 被动名称、说明、解锁条件、已有参数及结构化规则/能力状态 | 说明、培养条件、属性/效果解析 |
| constellations | 六个命座的名称、说明、参数、天赋加级等已核验规则 | 命座显示、天赋上限与计算 |
| capabilities | 文本已收录、数值已收录、具体规则是否支持及原因，按技能/效果声明 | 用户提示与计算阻断 |
| 标识和版本 | kind、schemaVersion、稳定ID、修订、游戏ID、内容版本及必要派生关系 | 查询、复制、文件、快照 |

角色定义的主要验收是介绍、技能、数值和规则完整且实际被使用。头像等展示资源由统一资源清单按角色/技能ID关联；详细仓库路径、采集哈希和精度审计放在工具侧清单中，不要求每个角色重复一套资源路径与溯源结构。资源和数据审计仍按各自章节完成，但不作为角色内容模型的中心。

每个技能参数使用稳定的局部ID、明确单位和等级序列。说明中的参数标签和计算规则引用同一个参数ID；培养等级、命座加级和命中段也通过该定义获取。不再单独维护character-talent-display这种可独立漂移的展示规则表。

正式元数据不采用每字段不同格式，也不将不同角色做成不同schema。未知或未取得的值用显式状态表达，不用零值填满。旅行者形态按元素分别定义并记录共有来源。

JSON使用UTF-8无BOM、LF、两空格缩进及末尾换行，不支持注释；有意义数组顺序和合法数值精度保持。说明与来源使用正式字段，长篇设计说明留在docs。内置复制是实际定义的派生，空白创建不预填虚构倍率、Buff或玩家条件。

### 展示与计算的连接

```text
固定来源的文本与数字 + 人工核验的参数绑定和机制
                        ↓ 统一角色契约与来源/精度检查
                 characters/<id>.json
                   ↙                  ↘
           展示、培养和说明         当前计算规则读取
                   ↘                  ↙
                 同一版本的角色/配装快照
                          ↕
                    自定义编辑与文件往返
```

UI可延迟加载长说明和详情，运行分块也可按用途投影，但所有投影必须由同一正式定义生成，并能按ID/修订还原对应参数。禁止在组件、store、生成器另写角色特例或从中文说明推断计算支持。

文本负责展示与解释，计算读取显式结构化规则。已有求值节点按语义拆分复用，因真实机制不足才增加最小能力，不引入任意脚本或第二套虚拟机。文本中的格式标记只允许受控渲染；不能直接将自定义文件中的HTML交给v-html执行。

收录全部可追溯文本和参数不表示全部机制可算。无法核验的技能、被动和命座仍可查看原说明和数值，计算时明确报未支持，不能忽略后输出“完整结果”。

### 必须展示的实用证据

1. 打开琴的定义，看到源资料中的角色介绍、技能说明、被动与命座说明，实际数值表由同一参数集合生成。
2. 在已记录且当前能力支持的真实配装上，核对定义中参数如何进入伤害公式；期望独立计算，不以引擎输出作为真值。
3. 显式复制为自定义试配，修改一个合法技能参数，参数显示与对应命中计算同时更新；导出、关闭、导回后文本、数值、规则和结果保持。
4. 老项目使用其自己的快照，不因目录或文本更新而静默换数值。当前账号、实物ID、穿戴、展柜和独立组合不被自定义操作回写。

静态角色资料可证明定义结构和来源，不能冒充玩家资料；如果实际配装与支持条件不匹配，该项计算验收保留材料缺口，不静默改命座来伪装原始案例。

## 四、精度和来源：先证明，再采用

### 能得到什么，以及目前不知道什么

genshin-db同时提供[数值参数表](https://github.com/theBowja/genshin-db/blob/8e5badd60b5d894284ccc927a56c9683529d2592/src/data/stats/talents.json)与[技能文本/参数标签](https://github.com/theBowja/genshin-db/blob/8e5badd60b5d894284ccc927a56c9683529d2592/src/data/ChineseSimplified/talents/jean.json)，可取得比游戏界面格式化显示更细的参数，但不能推断其每个字段都保留了底层导出的全部精度。

当前琴倍率2.92与旧表2.9200000762939453的差异不直接证明后者更准。本轮独立计算确认`Math.fround(2.92)`恰为`2.9200000762939453`，说明这组差异与float32展开相符；它仍不能单独证明旧表的来源和正确性。须追溯源数据及转换过程，不能按小数位多少决定采用哪一份。

更底层的Excel配置是候选审计来源，包括角色基础值/成长/突破、技能参数和圣遗物主副词条配置。本轮尝试在线读取现有资源仓库固定提交的技能/主词条原始表，未成功取得，不能将候选源记为已验证。实施时必须实际拿到对应固定版本文件再确认精度。

[Enka接口](https://github.com/EnkaNetwork/API-docs/blob/master/api_chs.md)提供实际展柜的培养、装备、战斗属性及附加词条ID；它适合玩家快照和交叉核对，不能自动替代所有基础表或从显示值无损倒推出原始精度。

### 固定的精度规则

- 保存原始文件字节，记录源提交、游戏版本（未知则明确未知）、字段路径、单位、原始表示与转换步骤。抓取时间不能冒充游戏版本。
- 原始值、推导值与显示值分开。显示取整只发生在展示层；计算参数不先按界面格式化再解析。
- 已截断或舍入的源值不能靠补零、插值或浮点展开恢复。源不够精确就标记精度限制，并寻找可验证替代来源。
- 数值运算先使用明确的Number策略；精确重现float32逐步舍入或十进制运算须有实际对照依据，不先全局增加任意精度库。
- 跨版本来源必须说明字段兼容性；不能将不同版本中“小数位最多”的字段随意拼接。
- 高精度修正导致数值变化时，单独列出旧值、新值、来源、独立期望与影响。不得混在改目录的差异里，也不得回写旧项目快照。

当前game-data/data/sources中的原始捕获归入`tools/data/sources/<来源>/<提交>/`，只读保存实际采用的最小原始文件、来源版本、路径和采用字段说明，不复制整个上游仓库，也不再裁掉字段后冒称原始文件。原始文件和正式定义有来源→采用的关系，不能双向编辑。外部ID适配表归game-data/data/mappings，采用过的有效规则只在正式实体内维护。

来源捕获可生成待审阅的实体差异，但不能覆盖正式JSON。原始文本/数值、字段绑定及人工规则分别核对，确认后合并，再离线生成运行数据。构建与普通测试使用正式资料和仓库内采用证据，不临时联网或依赖忽略的参考克隆。

### 移除旧主词条来源的门槛

建立主词条0—20级、成长和突破的逐字段来源/精度表。特别核对精通186.5与显示187等已有分歧，不能用另一份显示表替换后声称获得高精度。

只有替代数据实际取得并核验后，才能移走仍在提供该数据的旧表。未解决时明确停在该数据迁移步骤，不宣布全部清理完成、不继续从archive读取、不伪造“已核验”标记。

## 六、测试、固定输入和素材的统一管理

### 测试与fixtures

[Vitest允许配置任意测试匹配目录](https://vitest.dev/config/include.html)，并不规定必须并置。集中放tests是本项目的维护决策。单测按工作包镜像目录，跨模块、浏览器、桌面和性能分别组织，统一根命令调用。

生产src中不放*.test.ts、*.spec.ts、testing/或仅测试使用的样本构造器。迁移时同步相对导入、路径别名、TS项目、架构检查和CI；测试通过公共入口或明确的模块测试入口访问实现，不把内部所有函数都扩成产品API。

tests/fixtures按内容域组织，每份保留用途、版本及观测边界，真实原响应保留必要的完整性校验。固定输入与expected是输入/独立期望关系，测试输出和trace进artifacts。fixtures不是应用内置数据，也不是玩家真实数据的保证。

2026-11-10用户复审决定：历史构造fixture及专用测试/辅助代码直接删除，归档副本一并清理。保留当前功能使用的真实录存；新增边界由真实来源透明派生，不新增虚构角色、Buff、库存或伤害序列。私有原始文件继续忽略，仅登记安全的来源清单，不因统一目录而公开用户资料。

### 资源

assets是可维护资源的唯一根。每个资源ID指向唯一正式文件，来源配置、必要原始SVG、转换策略、许可证引用和哈希都能从manifest追溯。角色元数据只引用资源ID，不写web/public或某个组件的物理路径。

构建输出需要分发副本：由资源manifest确定性生成web/generated索引并复制到构建目录的assets路径；这些是生成物，不是第二套维护资源。原web/public分类、src/assets/ornaments、web/data/icons等在消费者迁完后移除；空charts目录一并清理。许可证原件继续统一在licenses。

验证资源ID完整性、文件哈希、来源、未使用项与既有缺口，检查网页根/子路径和桌面相对路径。缺失资源显式回退，不借用其他角色图片掩盖缺口。

`tools/lib`只容纳已存在多个调用者的JSON读取、路径、哈希、TS加载等工具代码，不建立万能utils目录或通用插件框架，也不存放业务求值器。工具数据保持在tools/data，来源原件、参考索引和迁移清单按用途区分，不和脚本混放。

### 命令契约

1. 根package.json的pnpm命令是正式入口；tools/README只索引，完整命令用途/输入/输出/是否联网/写入范围写在docs/guides的工具说明中。每个命令只有一份实现，旧同义入口在迁移后删除。
2. 数据/素材的采集是显式联网动作，不由dev/build/test/check暗中触发；生成默认离线，读取正式输入，不覆盖作者文件。
3. `--check`不修改正式输入或现有产物，只可在临时目录做确定性比较；失败返回非零并指出文件、字段或命令。不得靠默认补值/忽略错误制造检查通过。
4. 清理支持`--dry-run`，目标限定为核实过的生成目录；交付候选、用户文件和原始证据不被普通生成覆盖。写产物在全部验证后完成，失败不留下被误认成功的半份输出。
5. 移动脚本后统一从仓库根定位路径，不依赖脚本旧深度或调用者cwd；同步Vite/TS加载、架构白名单、fingerprint、CI、打包路径与说明。
6. 继续支持既定Node22.12+、pnpm11.3.0和CI Node24；依赖由实际拥有该工具的manifest声明，不靠偶然提升的传递依赖。没有现实需求不顺带升级工具链或增加语言/框架。
7. 操作性检查工具验证仓库约束和构建产物；功能断言、真实案例、固定测试输入和交互流程必须留在tests，不能用“check”改名绕过测试集中规则。

### tools整理验收

提交每个现有脚本的保留/合并/移动/归档清单和根命令对应表；所有正式命令均能找到唯一实现。对当前命令完成Windows及CI Linux相关路径核对，不混入只在本机成立的绝对路径。

验证普通生成/检查不联网、不写源文件、不会读取archive；验证构建、许可、交付和当前性能检查已切断旧内核引用。tools/desktop、阶段命名测试脚本、退休造例脚本和无消费者的试验入口退出当前工具树。

## 十、最终验收条件

- 正式schema按内聚业务单元拆分；无重复结构或阶段巨型入口；类型与运行时校验共用。
- 角色介绍、技能/被动/命座文本、数值、参数绑定与规则在同一可导出的定义中，参考成熟项目组织并由相关UI与计算实际读取；资源和采集溯源在各自系统维护，不喧宾夺主。
- 全角色使用相同结构；内容收录与机制支持分别声明；现有目录不因未知参数被伪装成全机制支持。
- 旧内核、旧表、相关导出/测试/fixture/性能和发布路径退出正式依赖图；archive不参与任何默认命令。
- 活跃业务代码/文案/新文件没有P3等阶段命名；旧阶段字符串仅在历史归档中存在。
- src无测试；活跃测试、helpers和固定输入均在tests；src无生产→测试反向依赖，根fixtures不再存在。
- 资源只有根assets作为维护真值；构建副本/索引均可重建；没有散落的手写资源映射或角色数值表。
- docs完成去留映射；已认可范式有唯一权威说明、代码落点和落实状态；规范、操作指南、计划与历史分清，所有当前命令/链接有效。
- tools完成逐脚本分类与根命令对应表；运行代码/测试/退休工具归位，普通生成与检查无隐式联网/源文件写入，CI和发布读取当前产品版本。
- 精度审计覆盖所有采用数值族，保留原始依据、版本、单位和转换；未验证来源/值保持缺口，不以兼容旧值掩盖。
- 真实458件库存与已有展柜按各自来源验证，不混账号；文件取消/失败、穿戴、脱库快照、组合和候选独立性保持。
- 功能检查按改动选取；最终冻结后串行执行浏览器/桌面与根/子路径生产检查、单worker、原体积预算。性能用当前产品真实输入；无真实整轴材料时明确不能宣称整轴性能或游戏观测验收。
