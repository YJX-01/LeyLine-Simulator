# 机制开发与验证

## 从正式入口走一遍

1. 在 `tools/data/README.md` 的“计算支持与验证资料”定位已支持的行为和固定来源。在 `src/game-data/data` 找正式角色、武器、套装或动作，确认身份、命中段、元素、倍率单位、精度、触发者和受益者。名称相似、单个读数接近的映射先保留为候选。
2. 用正常入口描述缺口。例：能手动勾选武器加成，但时间轴记录持有者造盾后加成没有开启。相同症状可能来自正式绑定、输入控件或缺失的事件。先确认缺的是哪一项，再动对应模块。用 `node tools/scripts/data/review-calculator-cards.mjs varesa` 可查看一个角色的卡片与命中 ID。
3. 实体数值和适用范围放在正式 JSON。优先复用已有公式、选择器和限时效果；通用伤害、反应算法及新模板归 `src/engine`，契约归 `src/schema`。内置与自定义角色共用 `CharacterMetadata`。保留旧 ID 和手动确认入口，检验计算器或时间轴能选到新增行为。
4. 用独立来源推导期望，从正常计算入口取实际值。伤害选足以区分公式的输入，例如改变目标数后同时核对基础伤害和命座加值。Buff 核对触发前、启用、禁用三种读数，注明授予者及受益者。来源写了刷新、叠层、到期或前后台限制时，再补相应边界。

## 三个容易误判的现象

| 现象 | 如何区分 |
| --- | --- |
| 真实武器事件已记录，但所有精炼档都没有加成 | 核对事件主体、种类及顺序，然后检查探针是否手动设置了 `windowFact=false`。验证事件触发时保持未指定；另用显式 true/false 验证手动覆盖。现有例子在 `tools/lib/roster-equipment-evaluation.mjs`。 |
| 新增队友 Buff 后，旧命中或映射变成未知 | 查看 `requiredInputs` 属于持有者、受益者、目标还是队伍。在确属中性场景的那一方明确填写未启用状态，按原容差复算。真实项目里没有记录的事实保留未知。 |
| 一次命中运行失败或读数异常 | 查输入是否合法，例如反应是否选了第二元素、效果是否要求角色本人。保留无效输入的诊断，用合法输入重跑。核对实际面板、命座、反应、单位和版本，并与独立期望比较。 |
