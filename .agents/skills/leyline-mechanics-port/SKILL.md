# LeyLine 项目开发

先确定用户在哪个入口操作、操作前后应看到什么、哪份数据应该改变。用户只问进展或要求复盘时，读取现有差异、报告和日志，注明证据对应的版本或时间。

## 按问题找入口

| 用户遇到的问题 | 先看哪里 |
| --- | --- |
| 某一击算不了、装备条件无效、要移植角色、两侧结果不一致 | [机制移植与 Mona 审计](references/mechanics-audit.md) |
| 展柜重复入库、组合应用后条数变了、保存或取消影响了其他配置 | [产品功能与数据归属](references/product-workflows.md)的账号、库存和配装部分 |
| 计算器有数值而轴上显示未知，或编辑后又显示旧结果 | [产品功能与数据归属](references/product-workflows.md)的计算器、时间轴和 Worker 部分 |
| 新增正式数据或图标、导入自定义角色、改页面、排查桌面与网页差异、准备交付 | [日常开发与交付](references/development.md) |

项目优先支持独立计算器中的单次命中和明确条件。遇到时序自动推导、多贡献者或多段暴击等需求，先查 `docs/product-direction.md` 的当前范围。指南中的项目路径从仓库根目录解析。

## 主 agent 和子 agent 共用的做法

- 主 agent 以可交付行为排批，例如“持有者造盾后，场上队友下一击能得到加成”。先核对是否已有正式实现，再决定补数据、修产品入口或补证据。用户要求并行时，以实际可用的 Terra 席位分配独立实体或功能；共享契约、引擎或持久化文件各留一名负责人。
- 子 agent 接收一个具体边界。从用户入口追到负责数据或行为的模块，在分配范围内实现并返回文件、实际读数和仍未知的条件。已有实现只缺证据时如实登记。共享接口有冲突时把具体依赖交给负责人。
- 交接可以直接写成「使用 `$leyline-mechanics-port` 处理【用户入口与行为】。可写【范围】，共享接口由【负责人】负责。按【复现场景】返回改动、证据及缺口，只做短验证。」

## 验证和汇报

按[仓库测试约定](../../../AGENTS.md#testing)选择验证范围。估时要计入初始化和目录扫描，例如 `pnpm data:check` 会连带执行多项检查。工具的 `yield_time_ms` 只决定何时返回进度。

先汇报用户新增能做什么，再分别列新增证据、恢复的旧行为或读数、仍需确认的范围。交付需要的完整验收与当前短验证分别记录；报告中断、缺失或早于最后改动时，标明未验证部分。
